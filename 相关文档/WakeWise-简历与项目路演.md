## 1. 一句话项目描述

**WakeWise（知晨）— AI Morning Assistant：**面向天气与个人行为动态变化设计智能晨间决策系统，基于 Java 21、Spring Boot、MySQL、Quartz 与原生 Android 构建夜间 Morning Agent（LLM 解释文案已接 OpenAI 兼容端点、Spring AI、Redis、RabbitMQ 为下一阶段规划），通过风险约束优化和用户行为学习生成可解释的最佳唤醒计划，并以端侧本地闹钟、计划 ACK 和降级策略保证关键任务可靠执行。

## 3. 面试介绍（约 90 秒）

我做的项目叫 WakeWise，中文名“知晨”。它不是普通天气闹钟，而是一个 AI Morning Assistant。

这个项目解决的问题是：用户真正关心的通常不是七点响铃，而是八点四十五能不能按时到公司。天气、交通、日历和个人准备速度每天都在变化，固定闹钟却完全不理解这些约束。

系统会在夜间由 Morning Agent 汇总次日天气、真实通勤 ETA（高德路径规划，失败回落手填分钟）与用户历史行为，日历导入已实装。核心算法不使用“下雨提前十分钟”这种简单规则，而是分别估计起床延迟、准备时间和通勤时间的概率分布，再根据事件重要性选择相应分位数，并在用户设置的最大提前、最大延后范围内，最小化迟到成本、睡眠损失和计划变化成本。

架构上，我刻意没有让大模型直接修改闹钟。解释文本默认由模板引擎生成、只引用计划事实；配置 OpenAI 兼容端点（`LLM_BASE_URL`/`LLM_API_KEY`/`LLM_MODEL`，DeepSeek/通义/Kimi/OpenAI 均可）后由 LLM 改写——提示词只含引擎算好的事实并明令禁止编造时间，失败即时回落模板，Spring AI 框架接入为可选演进。确定性决策引擎输出结构化 WakePlan，边界判定检查置信度与最大调整范围，最终由原生 Android 客户端（AlarmManager 精确闹钟 + Room 离线缓存 + outbox 事件补报）写入系统本地闹钟。只有设备返回 ACK，新计划才算生效；如果网络、天气 API 失败，旧闹钟仍然保留。

这个项目的亮点不是简单接入 LLM，而是把 Agent、可解释决策、行为学习和关键任务可靠性组合成了一个完整闭环。长期目标是扩展到手表、智能家居和车辆，形成 Morning OS。

## 4. 五分钟项目 presentation

### 0:00—0:40｜问题：闹钟准时，用户为什么还会迟到？

大家好，我的项目叫 WakeWise，中文名“知晨”。它的定位是 AI Morning Assistant。

传统闹钟解决的是“在七点钟响铃”，但用户真正的目标可能是“八点四十五前到公司”。如果明天暴雨、公交延误，或者临时增加了一场早会，七点这个静态数字并不会自动变化。用户只能在睡前打开天气、地图和日历，自己估算并修改闹钟。

所以 WakeWise 的目标不是 Wake on Time，而是 Wake at the Right Time。

### 0:40—1:25｜产品：从时间工具到目标驱动的晨间助手

用户可以创建两类目标：固定起床和目标到达（几点前必须到）；最晚出门、日历事件为规划。系统在晚上十点读取已授权的数据，生成下一次晨间计划。

首页不只显示闹钟时间，还会告诉用户：为什么调整、调整多少分钟、当前置信度是多少、数据什么时候更新，以及如何一键撤销。

为了建立信任，产品提供三级自动化：仅观察（L0）、每次确认（L1）、边界内自动（L2，需置信度≥0.70 且只提前不延后）；全流程设备协同为规划。新用户默认先使用低自动化等级，而不是一上来就让 AI 接管闹钟。

### 1:25—2:25｜算法：不是天气加权，而是风险约束优化

WakeWise 把晨间过程拆成三个随机变量：从响铃到离床的时间、从离床到出门的准备时间，以及从出门到目的地的通勤时间。

系统预测这三段耗时的分布。普通日程可以使用 P75，重要会议、航班或考试可以使用 P90 或 P95。目标到达时间减去总耗时分位和安全余量，就得到候选唤醒时间。

随后把候选时间截断到用户允许的窗口内（最大提前/延后、不晚于目标前 15 分钟），并用“平静期规则”控制计划变化成本——无风险信号且提前量不足 10 分钟时不折腾。迟到概率用正态 CDF 闭式计算，与推荐值一起写入计划供审计与回放。

天气、交通、行为、日历和季节分数主要用于特征监控和解释，不是简单线性相加后直接换算分钟。这能避免“同样下雨，步行和地铁用户却提前相同时间”这种粗糙结果。

### 2:25—3:30｜AI Agent：自主，但不失控

Morning Agent 当前实现为 Quartz 夜间任务（22:00，幂等：同目标日旧 PROPOSED 计划自动作废）：采集天气与行为先验，构建评估上下文，调用决策引擎生成 WakePlan，再经自动布防判定检查置信度、调整方向与最大提前范围。“有状态、可恢复、多工具编排”的完整 Agent 形态为下一阶段（规划）。

这里有一个重要设计：大模型不直接决定最终时间。解释生成已接 OpenAI 兼容 LLM 端点（用户可配，默认关闭即纯模板；提示词只含决策记录中的事实，不能自己编造“明天会堵车”，失败回落模板）；Spring AI 负责自然语言意图与工具选择属接入规划；关键时间始终来自确定性的预测与约束模块。

对于未来的 MCP 扩展，每个工具都声明输入输出 Schema、权限范围、超时和幂等策略，外部内容一律当作不可信数据，不能变成系统指令。

### 3:30—4:20｜架构与可靠性：AI 可以失败，闹钟不能跟着摆烂

客户端为原生 Android（Java 17 + ViewBinding + Room + AlarmManager 精确闹钟 + WorkManager 同步，响铃页直接展示晨间简报与决策原因）。后端使用 Java 21 和 Spring Boot，MVP 采用模块化单体；MySQL（Flyway 迁移）保存事务和审计数据，Quartz（22:00）负责夜间计划。Redis/RabbitMQ 属 V1 规划——当前以模块内缓存、站内通知与客户端轮询同步替代。

云端只负责生成更聪明的计划，真正响铃由端侧本地系统完成。服务端下发新计划后，客户端先创建新闹钟并返回 ACK，再删除旧计划。任何一步失败，旧闹钟继续有效。推送只是通知和补偿渠道，不是唯一执行机制。

外部 API 失败时，系统使用缓存或历史分位值，并显示低置信度；后端完全不可用时，已下发的固定闹钟仍然照常响。

### 4:20—5:00｜价值、指标与未来

项目的北极星指标是晨间计划成功率，同时观察智能计划采纳率、迟到风险下降、准备时长预测 MAE 和无效早起分钟数。系统是否越来越聪明，要用预测误差和任务结果证明，而不是看模型有多大。

未来 WakeWise 会接入 Apple Health、智能手表、Home Assistant、车辆和语音助手，让灯光、窗帘、温控、咖啡机和出行计划共同协作，最终形成 Morning OS。

这个项目最核心的价值，是把多源环境感知、AI Agent、可解释决策、个性化学习和关键任务可靠性放进了同一个工程闭环。谢谢。

## 5. 高频追问与回答卡

### Q1：为什么不用 LLM 直接计算起床时间？

LLM 的输出具有随机性，也可能受提示注入或错误上下文影响。闹钟属于高影响动作，所以 LLM 只负责语义理解、工具编排和解释；最终时间由结构化特征、确定性约束和可版本化模型计算，方便测试、审计和回滚。

### Q2：天气预报或交通 API 不准怎么办？

系统不把单点预测当事实，而是记录数据新鲜度、质量和 P50/P90 等分位值。外部服务失败时按“新鲜缓存 → 历史同路线分位 → 保留原计划”降级。置信度不足或变更过大时请求用户确认。

### Q3：为什么同时提 Spring AI 和 LangChain4j？

生产基线选择 Spring AI——接入属下一阶段：当前解释层已通过自研 OpenAI 兼容轻量客户端接入 LLM（Boot 3.3 钉版不升，Spring AI 1.0 官方仅支持 3.4+），模板兜底，`ExplanationGenerator` 应用层端口保留随时替换为 Spring AI 的能力。LangChain4j 作为 Java AI 生态的备选和实验对照，不在 MVP 同时承载同一条链路，避免双框架复杂度。

### Q4：Quartz 会不会在多实例中重复执行？

当前不会：MVP 用内存 JobStore 单实例部署，不存在集群重复触发。业务层已有幂等保护——同目标日的旧 PROPOSED 计划在重新评估时自动作废（SUPERSEDED），计划状态机阻止重复下发。多实例场景升级 JDBC JobStore + 集群模式属扩展项。

### Q5：RabbitMQ 挂了闹钟会不会不响？

不会。当前实现没有引入 MQ——通知走站内信，计划同步由客户端 WorkManager 轮询完成（拉 pending → 端侧调度 → 回 ACK），事件上报失败落本地 outbox 补报；可靠性不依赖任何消息中间件。移动端已保存的本地闹钟完全离线有效，新计划未 ACK 前旧计划不取消。（引入 MQ 做异步计算与重试属 V1 规划。）

### Q6：用户行为学习如何避免越学越偏？

一期已实装的机制（SHRINK_V1）：样本取真实起床延迟（dismissedAt − triggeredAt，贪睡计入延迟是特性而非 bug）；单条样本截断到 60 分钟防“开着闹钟人不在”的病态数据；估计用经验分位数与全局先验收缩混合，样本不足 5 条直接保持先验，校准只在关闭事件后重算——更新天然缓慢，不会因单次异常大幅漂移；方差带下限防退化，modelVersion 标注 `+CAL(n=N)` 全程可审计。规划中：时间衰减、节假日/旅行样本过滤、影子评估与用户手动重置。

### Q7：项目最大的技术难点是什么？

不是接入天气或 LLM，而是同时满足智能性、可靠性和用户控制。计划必须利用不确定数据做个性化决策，又必须保证在网络、推送、模型和第三方服务失败时不漏响，还要让用户理解并撤销每次自动动作。

### Q8：这是微服务项目吗？

MVP 不是。初期使用模块化单体保持事务简单和交付效率，领域边界按 Alarm、Context、Decision、Agent、Notification 划分。只有在任务吞吐、团队边界或独立扩缩容形成真实需求后，才优先拆分 Worker 服务。

### Q9：MCP-ready 体现在哪里？

Morning Agent 的工具拥有稳定名称、JSON Schema、权限范围、超时、幂等键和审计日志，这些能力与 MCP 工具模型兼容。未来接入第三方 MCP Server 时仍经过 allowlist、用户授权和策略守卫，而不是让模型任意调用外部能力。

### Q10：如何证明产品有效？

进行分阶段实验：先用影子模式比较系统建议与用户实际设置；再进行“仅建议”实验观察采纳率；最后对自愿开启自动化的用户比较晨间计划成功率、迟到率、无效早起时长和睡眠保留分钟数。任何收益都要同时看护栏指标，不能靠一味提前闹钟换取准时率。

## 6. 演示建议

五分钟现场演示只展示一条完整故事线：

1. 创建“08:45 到公司”的目标型闹钟。
2. 模拟次日暴雨（天气为 Open-Meteo 真实数据；配 `AMAP_KEY` 与常驻地址后通勤为高德真实耗时，未配置时用方式系数近似）。
3. 展示 07:00 → 06:45 的计划变化、主要因素与置信度。
4. 在 doc.html 计划详情中比较原计划和推荐计划的迟到概率（app 内对比页为规划）。
5. 点击确认，展示设备 ACK 后状态从 `DISPATCHING` 变为 `ARMED`。
6. 停掉后端模拟云端不可用：本地闹钟照常、响铃页简报走离线兜底，证明端侧可靠性。
7. 关闭闹钟 → 通知栏出现“出门打卡”→ 点【我出门了】→ 后端 `wake_history.left_home_at` 落库，展示行为学习数据回流闭环。
8. （规划，暂不可演示）一句话“明天会议改线上”生成提案、二次确认后修改。

这条演示能同时覆盖产品价值、算法、可靠性、行为学习闭环和安全边界，信息密度最高。
