## 1. 一句话项目描述

**WakeWise（知晨）— AI Morning Assistant：**面向天气、交通与日程动态变化设计智能晨间决策系统，基于 Java 21、Spring Boot、Spring AI、Flutter、Redis、MySQL、RabbitMQ 与 Quartz 构建 Morning Agent，通过风险约束优化和用户行为学习生成可解释的最佳唤醒计划，并以端侧本地闹钟、计划 ACK 和降级策略保证关键任务可靠执行。

## 3. 面试介绍（约 90 秒）

我做的项目叫 WakeWise，中文名“知晨”。它不是普通天气闹钟，而是一个 AI Morning Assistant。

这个项目解决的问题是：用户真正关心的通常不是七点响铃，而是八点四十五能不能按时到公司。天气、交通、日历和个人准备速度每天都在变化，固定闹钟却完全不理解这些约束。

系统会在夜间由 Morning Agent 汇总次日第一个关键日程、天气、路线 ETA 和用户历史行为。核心算法不使用“下雨提前十分钟”这种简单规则，而是分别估计起床延迟、准备时间和通勤时间的概率分布，再根据事件重要性选择相应分位数，并在用户设置的最大提前、最大延后范围内，最小化迟到成本、睡眠损失和计划变化成本。

架构上，我刻意没有让大模型直接修改闹钟。Spring AI 负责理解自然语言、调用工具和生成解释，确定性决策引擎输出结构化 WakePlan，策略守卫检查权限和边界，最终由 Flutter 客户端写入系统本地闹钟。只有设备返回 ACK，新计划才算生效；如果网络、天气 API 或推送失败，旧闹钟仍然保留。

这个项目的亮点不是简单接入 LLM，而是把 Agent、可解释决策、行为学习和关键任务可靠性组合成了一个完整闭环。长期目标是扩展到手表、智能家居和车辆，形成 Morning OS。

## 4. 五分钟项目 presentation

### 0:00—0:40｜问题：闹钟准时，用户为什么还会迟到？

大家好，我的项目叫 WakeWise，中文名“知晨”。它的定位是 AI Morning Assistant。

传统闹钟解决的是“在七点钟响铃”，但用户真正的目标可能是“八点四十五前到公司”。如果明天暴雨、公交延误，或者临时增加了一场早会，七点这个静态数字并不会自动变化。用户只能在睡前打开天气、地图和日历，自己估算并修改闹钟。

所以 WakeWise 的目标不是 Wake on Time，而是 Wake at the Right Time。

### 0:40—1:25｜产品：从时间工具到目标驱动的晨间助手

用户可以创建四类目标：固定起床、最晚出门、必须到达和日历事件。系统在晚上十点读取已授权的数据，生成下一次晨间计划。

首页不只显示闹钟时间，还会告诉用户：为什么调整、调整多少分钟、当前置信度是多少、数据什么时候更新，以及如何一键撤销。

为了建立信任，产品提供四级自动化：只观察、每次确认、边界内自动、全流程设备协同。新用户默认先使用低自动化等级，而不是一上来就让 AI 接管闹钟。

### 1:25—2:25｜算法：不是天气加权，而是风险约束优化

WakeWise 把晨间过程拆成三个随机变量：从响铃到离床的时间、从离床到出门的准备时间，以及从出门到目的地的通勤时间。

系统预测这三段耗时的分布。普通日程可以使用 P75，重要会议、航班或考试可以使用 P90 或 P95。目标到达时间减去总耗时分位和安全余量，就得到候选唤醒时间。

随后系统遍历用户允许窗口中的候选时间，综合迟到成本、睡眠损失、计划变化成本和低置信度惩罚，选出最佳可行解。

天气、交通、行为、日历和季节分数主要用于特征监控和解释，不是简单线性相加后直接换算分钟。这能避免“同样下雨，步行和地铁用户却提前相同时间”这种粗糙结果。

### 2:25—3:30｜AI Agent：自主，但不失控

Morning Agent 是一个有状态、可恢复、可审计的任务编排器。它由定时器触发，先通过工具获取天气、交通、日历和行为摘要，再构建统一 MorningContext，调用决策引擎生成 WakePlan，最后经过 Policy Guard 检查权限、置信度和最大调整范围。

这里有一个重要设计：大模型不直接决定最终时间。Spring AI 负责自然语言意图、工具选择和解释生成；关键时间来自确定性的预测与优化模块。解释只能引用决策记录中的事实，不能让模型自己编造“明天会堵车”。

对于未来的 MCP 扩展，每个工具都声明输入输出 Schema、权限范围、超时和幂等策略，外部内容一律当作不可信数据，不能变成系统指令。

### 3:30—4:20｜架构与可靠性：AI 可以失败，闹钟不能跟着摆烂

客户端使用 Flutter，但闹钟调度通过 iOS 和 Android 原生适配实现。后端使用 Java 21 和 Spring Boot，MVP 采用模块化单体；MySQL 保存事务和审计数据，Redis 保存热上下文和短期 Agent 状态，RabbitMQ 处理异步通知与重试，Quartz 负责夜间计划和复核。

云端只负责生成更聪明的计划，真正响铃由端侧本地系统完成。服务端下发新计划后，客户端先创建新闹钟并返回 ACK，再删除旧计划。任何一步失败，旧闹钟继续有效。推送只是通知和补偿渠道，不是唯一执行机制。

外部 API 失败时，系统使用缓存或历史分位值，并显示低置信度；后端完全不可用时，已下发的固定闹钟仍然照常响。

### 4:20—5:00｜价值、指标与未来

项目的北极星指标是晨间计划成功率，同时观察智能计划采纳率、迟到风险下降、准备时长预测 MAE 和无效早起分钟数。系统是否越来越聪明，要用预测误差和任务结果证明，而不是看模型有多大。

未来 WakeWise 会接入 Apple Health、智能手表、Home Assistant、车辆和语音助手，让灯光、窗帘、温控、咖啡机和出行计划共同协作，最终形成 Morning OS。

这个项目最核心的价值，是把多源环境感知、AI Agent、可解释决策、个性化学习和关键任务可靠性放进了同一个工程闭环。谢谢。

## 5. 高频追问与回答卡

### Q1：为什么不用 LLM 直接计算起床时间？

LLM 的输出具有随机性，也可能受提示注入或错误上下文影响。闹钟属于高影响动作，所以 LLM 只负责语义理解、工具编排和解释；最终时间由结构化特征、确定性约束和可版本化模型计算，方便测试、审计和回滚。

### Q2：天气预报或交通 API 不准怎么办？

系统不把单点预测当事实，而是记录数据新鲜度、质量和 P50/P90 等分位值。外部服务失败时按“新鲜缓存 → 历史同路线分位 → 保留原计划”降级。置信度不足或变更过大时请求用户确认。

### Q3：为什么同时提 Spring AI 和 LangChain4j？

生产基线选择 Spring AI，因为它与 Spring Boot 的配置、安全和可观测体系更一致。LangChain4j 作为 Java AI 生态的备选和实验对照，不在 MVP 同时承载同一条链路。通过应用层端口保留替换能力，避免双框架复杂度。

### Q4：Quartz 会不会在多实例中重复执行？

使用 JDBC JobStore 和集群模式协调触发，同时在业务层用 `alarmId + targetDate + triggerType` 形成幂等键。即使任务重复进入，计划唯一约束和状态机也会阻止重复下发。

### Q5：RabbitMQ 挂了闹钟会不会不响？

不会。RabbitMQ 用于异步计算、通知和重试，不是最终闹钟执行面。移动端已经保存的本地闹钟不依赖 MQ。新计划未得到端侧 ACK 前，旧计划也不会被取消。

### Q6：用户行为学习如何避免越学越偏？

先对行为事件做来源和质量分级，过滤节假日、旅行、设备异常等离群样本；参数采用缓慢更新和时间衰减，不因单次异常大幅变化。新版本先进行离线回放和影子评估，再灰度生效，用户也可以纠正记录或重置个性化模型。

### Q7：项目最大的技术难点是什么？

不是接入天气或 LLM，而是同时满足智能性、可靠性和用户控制。计划必须利用不确定数据做个性化决策，又必须保证在网络、推送、模型和第三方服务失败时不漏响，还要让用户理解并撤销每次自动动作。

### Q8：这是微服务项目吗？

MVP 不是。初期使用模块化单体保持事务简单和交付效率，领域边界按 Alarm、Context、Decision、Agent、Notification 划分。只有在任务吞吐、团队边界或独立扩缩容形成真实需求后，才优先拆分 Worker 服务。

### Q9：MCP-ready 体现在哪里？

Morning Agent 的工具拥有稳定名称、JSON Schema、权限范围、超时、幂等键和审计日志，这些能力与 MCP 工具模型兼容。未来接入第三方 MCP Server 时仍经过 allowlist、用户授权和策略守卫，而不是让模型任意调用外部能力。

### Q10：如何证明产品有效？

进行分阶段实验：先用影子模式比较系统建议与用户实际设置；再进行“仅建议”实验观察采纳率；最后对自愿开启自动化的用户比较晨间计划成功率、迟到率、无效早起时长和睡眠保留分钟数。任何收益都要同时看护栏指标，不能靠一味提前闹钟换取准时率。

## 6. 演示建议

五分钟现场演示只展示一条完整故事线：

1. 创建“08:45 到公司”的目标型闹钟。
2. 模拟次日暴雨与公交拥堵。
3. 展示 07:00 → 06:45 的计划变化、主要因素与置信度。
4. 点击“查看分析”，比较原计划和推荐计划的迟到概率。
5. 点击确认，展示设备 ACK 后状态从 `DISPATCHING` 变为 `ARMED`。
6. 模拟交通 API 失败，证明系统保留本地计划并显示降级原因。
7. 用一句话“明天会议改线上”生成提案，但必须再次确认才能修改。

这条演示能同时覆盖产品价值、算法、Agent、可靠性和安全边界，信息密度最高。
